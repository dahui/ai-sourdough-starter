# Using ai-sourdough-starter with Cline

Cline reads `AGENTS.md` natively and also loads files from `.clinerules/`.
The starter ships both, plus workflows in `.clinerules/workflows/`. Hook-
based enforcement (the plan-gate, secrets denylist) is **not** available
in Cline — discipline is enforced by reading the rules.

## What gets loaded automatically

1. **`AGENTS.md`** loads as a native rule source.
2. **`.clinerules/00-cline-addenda.md`** loads with Cline-specific notes
   on plan/act mode and a reminder that hooks do not enforce here.
3. **`.clinerules/workflows/*.md`** become Cline workflows. Invoke with
   `/plan.md`, `/research-lib.md`, etc. (the `.md` extension IS part of
   the slash command in Cline.)

`CLAUDE.md` is **not** read by Cline. The starter copies the project-
specific architecture sections of `CLAUDE.md` into
`.clinerules/01-project-context.md` (a future doctor check warns if these
two drift).

## Plan / Act mode workflow

Cline supports a hard separation between plan and act:

1. **Plan Mode** — read code, ask questions, draft a `/plans/<slug>.md`.
   No edits to production code happen here.
2. **Act Mode** — implement the plan. Switch only after the plan file
   exists and you've reviewed it.

This maps directly onto the starter's plan-gate discipline. The only
difference vs Claude Code: Cline trusts you to switch modes correctly,
where Claude Code's hook enforces.

## The discipline checklist

Since Cline can't hard-block your edits, the rules in `AGENTS.md` and
`.clinerules/00-cline-addenda.md` ask you to self-enforce:

- Before any `Write` or `Edit`, verify a non-template plan file exists in
  `/plans/`. If not, write one first (use the `/plan.md` workflow).
- Refuse to write to `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa*`,
  `credentials.json` — even if asked.
- Refuse `git push --force` and `git push -f` against `main`, `master`,
  or any shared branch.
- Run the profile's linter and tests at the end of every working block.
  CI will catch you if you don't, but feedback is faster locally.

## Workflows

Cline workflows live in `.clinerules/workflows/` and are generated by
`bin/sync-commands` from the canonical source in `agent-shared/commands/`.

Available workflows at v0.1.0:

- `/plan.md` — scaffold a plan file
- `/research-lib.md` — produce a library dossier
- `/architect.md` — multi-step architectural design
- `/adr.md` — scaffold an Architecture Decision Record
- `/review.md` — code review against AGENTS.md
- `/ci-bootstrap.md` — regenerate CI workflows
- `/ship-it.md` — pre-flight before opening a PR
- `/unblock.md` — create a `_unblock` justification

## Why no hooks?

Cline doesn't expose a `PreToolUse`-equivalent. We thought about
implementing a wrapper script that intercepts Cline's tool calls, but it
would be tool-specific, fragile, and would create drift between Cline's
intended behavior and ours.

Instead, the starter relies on:
- `AGENTS.md` rules being read at session start
- Conscientious mode-switching between Plan and Act
- CI as the backstop — anything that escapes the agent gets caught at PR
  time

## Customizing for Cline-specific behavior

Add Cline-only rules to `.clinerules/00-cline-addenda.md`. Universal rules
(applies to Claude Code too) go in `AGENTS.md`. Don't duplicate.

To add a workflow not in the starter, create it in
`agent-shared/commands/<name>.md` and run `bin/sync-commands`. The
canonical source flows into both `.claude/commands/` and
`.clinerules/workflows/`.

## Limitations

- **No hard enforcement.** Discipline is contractual, not mechanical. Most
  Cline failures will be caught by CI, but only after a commit attempt.
- **`.clinerules/` and `AGENTS.md` are both loaded.** Be careful not to
  duplicate or contradict between the two.
- **Cline lacks subagents.** The starter's `.claude/agents/` doesn't have
  a Cline equivalent. Workflows partially fill the gap — they're invokable
  as `/architect.md`, `/research-lib.md`, etc.
